# S2J Content Dates Service - サービス仕様 (ドラフト)

採用・合意前の設計メモとして `docs_mod/` に置き、確定後は `docs/SERVICE_SPEC.md` に移行します。

## 概要

本ドキュメントは、S2J Content Dates Service の初期設計における、サービス全体の統合の見取り図を定義します。

## 目的

公開日 (created) と更新日 (modified) を **見える化する** ための、算出・判定・整形ロジックです。Similarity Service と同型の Composer ライブラリです。

対象は、コンテンツタイプ全体 (固定記事、投稿、CPT、任意でメディア) です。

本ライブラリは **WordPress 非依存** です。WP フック、設定画面、クエリー改変は扱いません。

### 位置付けの変遷

仕様検討の最初期では、固定記事、投稿、CPT を対象とし、プロジェクト名も S2J Post Dates Service (`s2j/post-dates-service`) でした。

その後、メディア (`attachment`) もターゲットに含めることにした際、「Post」では WP 内部の `WP_Post` には合いますが、日本語では投稿 (`post`) だけに読めるため、プロジェクト名を改称しました。

## 非目標 (本ライブラリ)

* `add_action` / `register_post_type` / `WP_Query` の実行。
* 管理画面 HTML、ブロック登録、REST エンドポイント。
* テーマの見た目 (色、テンプレート階層)。
* SaaS 送信、ピン留め一覧 (それぞれ別サービス)。

## 機能 (プロダクト観点)

通常、固定記事や CPT を表示すると公開日しか出ません。本エコシステムでは更新日も見える化します。

* 単体表示で、公開日に加えて更新日を出せる。
* 一覧 (Archive) の絞り込み / ソート条件に更新日を使える。
* 管理画面で、コンテンツタイプごとに次を制御できる (UI はプラグイン)。
    * 固定記事に更新日を出すか。
    * 利用中の各 CPT に更新日を出すか。任意タイプだけ出さない指定も可。
    * 更新日を出すと指定したタイプの Archive に、更新日のフィルター / ソートを足すか。
    * 可能ならメディアライブラリのコンテンツにも対応する。

## Composer ライブラリの理由

要件の見た目は WordPress 機能ですが、層は次に分かれます。

| 層 | 中身 | 置き場 |
| --- | --- | --- |
| 計算 | 日付の正規化、「更新を見せるか」、表示用レコード、一覧のソートキー、フィルター条件の組立、親タイプへの `max(modified)` 集約 | **本ライブラリ** |
| 副作用 | 設定テーブル、CPT ごとの on/off、メタ、Archive クエリー、出力、メディアライブラリ | **S2J Content Dates** (プラグイン) |

プラグイン一本にロジックを置くと、kis-core / s2j-legal / 将来のイベントプラグインで判定が複製され、ユニットテストも WP 一式が必要になります。

## 本ライブラリの責務

入力は WP オブジェクトではなく、**日付と設定のレコード** です。出力もレコードです。

| 責務 | 内容 |
| --- | --- |
| 正規化 | created / modified を比較可能な値にする (タイムゾーン済みの値を受け取る想定) |
| 表示判定 | タイプ設定 (および任意の個別指定) から、更新日を出すか否か |
| 表示レコード | 公開日・更新日の組、出す / 出さない、整形済み文字列の材料 |
| 一覧キー | ソートキー、フィルター比較用の値。`WP_Query` 自体は組まない |
| 集約 | 親子がある場合、子の `max(modified)` を親の更新日に使う (KIS の `product` / `product_section` を想定) |

メディア (`attachment`) も、サービスからはコンテンツタイプの1件です。アップロード日とファイル更新の対応付け、一覧 UI はプラグインです。サービス仕様では入出力の拡張点にとどめ、WP 実装は段階導入でよいです。

## プラグインの責務 (境界。詳細はプラグイン仕様)

指定 UI は、管理画面の **標準テーブル** ( `WP_List_Table` 相当) とします。1行 = 1コンテンツタイプです。見出しは「カスタム投稿タイプ」ではなく **コンテンツタイプ** です。

| 表示名 | タイプ | 単体で更新日を出す | Archive に更新日の絞り込み / ソートを足す |
| --- | --- | --- | --- |
| 固定記事 | `page` | on/off | 原則なし (`has_archive` がないため列は無効) |
| 投稿 | `post` | on/off | on/off |
| 各 CPT | 登録名 | on/off | on/off |
| メディア (任意) | `attachment` | on/off | メディア UI は別でも可 |

「テーマで enabled な CPT」は、この表の行の集合です。任意タイプだけ出さない指定は、該当行を off にすることで、対応します。

固定記事を CPT ではないからと別画面にせず、`page` を1行足します。Archive 列は、効かないチェックを置かず無効化します。

プラグインは、テーブルの状態を設定レコードに落とし、本ライブラリに渡します。メタ名は KIS 専用の `_kis_show_modified` ではなく、S2J 境界に合わせた `_s2j_show_modified` 等を検討します (確定はプラグイン仕様)。

## 設計方針

本ライブラリは [kis-wordpress エコシステム仕様](https://github.com/stein2nd/kis-wordpress/blob/main/docs_mod/specs.md) と同じく、FOP + Clean Coding を基本とします。Clean Architecture の定型分割は採用しません。

データの中身は純粋関数と不変レコードに閉じます。

| 借用する原則 | 本ライブラリでの意味 |
| --- | --- |
| 依存の向きは外 → 内 | 純関数は WordPress / HTTP を知らない |
| 内側はビジネスルール | 正規化、閾値、パイプライン組立はフレームワーク非依存 |
| 外側は詳細 | プラグインが WP と本ライブラリの間を翻訳する |

## 関連リポジトリ

呼び出し側の正は **S2J Content Dates** です。kis-core は本機能の本体にせず、必要なら当該プラグインを有効化 (または require) します。

| 名称 | 種別 | 役割 |
| --- | --- | --- |
| **本ライブラリ** | Composer | 日付レコードの正規化、表示可否、ソート / フィルター用キー、親への更新日集約 |
| **S2J Content Dates** (仮) | WP プラグイン | 管理画面、オプション、メタ、Archive の `WP_Query`、ブロック / テンプレート、メディア UI |
| [kis-wordpress](https://github.com/stein2nd/kis-wordpress.git) | モノレポ | サイト専用プラグイン群。日付機能は kis-core に抱え込まない |
| [kis2026_base](https://github.com/stein2nd/kis2026_base.git) | テーマ | 見た目。日付の正はプラグイン + 本ライブラリ |

## 実装順 (KIS エコシステムとの関係)

1. 本 repo でスケルトンと純関数の初版 (PHPUnit で WP なし)。
2. S2J Content Dates プラグインが Composer で require し、テーブル UI と出力をつなぐ。
3. KIS サイトでは当該プラグインを有効化し、kis-case 等と共用する。
4. 旧案の `packages/post-dates-service/` 仮置きは、本 repo へ寄せる (モノレポ仕様の更新は kis-wordpress 側)。

## 未決 (次の仕様で確定)

* 公開日と更新日が同日 (または差が閾値未満) のとき、更新日を隠すか。
* 新規に登録されたコンテンツタイプのデフォルトは on か off か。
* タイプのデフォルトに加え、個別コンテンツの指定を持つか。
* 整形フォーマット (例: `YYYY/MM/DD`) をライブラリが持つか、呼び出し側が持つか。
* 親への集約を汎用 API にするか、KIS 製品 CPT 向けの利用例にとどめるか。
